How guests pay, how staff verify and reconcile, and how guest emails and WhatsApp messages are sent and tracked.

## Payments

### Ways to pay

The hotel chooses which methods are offered (**Admin → Settings → Ways to pay**; `hotel_settings.payment_methods`). A gateway also needs its credentials on the server. If it's offered but not configured, guests see it greyed out as "Not available yet".

| Method | Kind | Ledger method | How it's confirmed |
| ------ | ---- | ------------- | ------------------ |
| Pay at the hotel | desk | cash / card / … | Staff record it at the desk ("Record payment") |
| Bank transfer | transfer | bank | Guest reports the transaction ID; staff verify it against the statement |
| bKash (send money) | transfer | bkash | Same, against the bKash merchant app |
| Nagad (send money) | transfer | nagad | Same, against the Nagad merchant app |
| bKash / Nagad / Card online | gateway | bkash / nagad / card | Only by the gateway's server-to-server answer (below) |

The guest's booking page (`/booking/manage`) handles full payment, the advance, and the outstanding balance. It defaults to the advance when one is due; "Pay the full balance" fills in the rest. Amounts can't exceed what's still payable, which counts transfers already being checked.

### Reported transfers

1. `guest_submit_payment(token, method, amount, txn_id, sender)` creates a `payments` row with `status = pending`, `source = guest`. Pending payments never count towards `amount_paid_bdt`.
2. It's refused if:
   - the method isn't offered (`METHOD_DISABLED`);
   - the transaction ID is malformed (`BAD_REFERENCE`);
   - the transaction ID was already used for that method on any booking (`DUPLICATE_REFERENCE`, enforced by a unique index);
   - the amount is above the open balance (`BAD_AMOUNT`);
   - the booking already has three reports waiting (`TOO_MANY_PENDING`);
   - the booking is cancelled or closed (`LOCKED`).
3. Staff with `payments.record` are notified and verify it with `admin_verify_payment`:
   - **Confirm received** turns it `confirmed` (receipt number, ledger, payment confirmation email).
   - **Not received** turns it `failed`. It needs a reason, which the guest sees in the payment-problem email.
4. `/admin/payments` lists everything waiting. Reconciliation flags anything unchecked for more than 24 hours.

### Gateways: never trust the browser

The only path to the ledger is `processInbound()` (`src/lib/payments/service.ts`) → `record_gateway_event()` → `apply_payment_callback()`:

1. **Signature.** A webhook whose signature fails is recorded with outcome `bad_signature` and goes no further. HTTP 401.
2. **Server-side verification.** We ask the gateway itself what happened:
   - **bKash:** `execute`, then `payment/status`.
   - **SSLCommerz:** the validation API by `val_id`, or by `tran_id`.
   Only the gateway's answer is used: status, whole-taka amount, its transaction id, and our intent id echoed back.
3. **Identity.** The confirmed payment must name the same intent as the notification. Otherwise it's recorded `unverified` and not applied.
4. **Replay protection.** `payment_gateway_events` is unique on `(provider, event_id)`. A replayed notification returns `replay` and changes nothing.
5. **Idempotency.**
   - `apply_payment_callback` applies an intent's result once. A repeat with the same reference is `duplicate`; a conflicting one is `ignored`.
   - `create_payment_intent` is idempotent by key. The guest's form sends one key per page load, so a double click doesn't create two intents.
6. **Safe updates.** The amount must equal the intent (`mismatch` fails the intent and emails the guest). A success that arrives after the intent expired is still applied, because the guest's money was taken. Ledger totals are recomputed by trigger, never set directly.
7. **Retry semantics.** If we can't reach the gateway to verify, nothing is recorded and the webhook answers 503, so the gateway's retry is processed normally. If the gateway says the payment is still pending, nothing is recorded either.

Browser returns (`/api/payments/[provider]/return`) only identify which payment to check. The guest is then shown `/booking/payment`, which reads the status from the database and refreshes until it's settled.

Intents expire 30 minutes after creation (`expire_payment_intents`, pg_cron every 5 minutes).

### Enabling a gateway

1. Get merchant approval and **sandbox** credentials from the provider.
2. Add them to Vercel Preview (staging) as **Sensitive** variables. Set `SSLCOMMERZ_SANDBOX=true` or the bKash sandbox `BKASH_BASE_URL`.
3. Point the provider's notification (IPN) URL at `https://<site>/api/payments/<card|bkash>/webhook`.
4. On staging:
   - switch the method on in Settings;
   - make a sandbox payment, then a failed one and a cancelled one;
   - check `/admin/payments` → Online payments shows `applied` with "signature ✓ · confirmed with gateway ✓", and reconciliation is clean.
5. Replace the credentials with live ones in Production, then switch the method on.

### Receipts and invoices

- **Receipts.** Every confirmed payment gets a receipt number (`RCP-YYYY-NNNNNN`), whichever path confirmed it. Staff open it at `/admin/receipts/[id]`; guests at `/booking/manage/receipt/[id]`, their own payments only.
- **Invoices.** One per booking (`INV-YYYY-NNNNN`), numbered the first time it's opened.
- **What an invoice shows:**
  - nights itemised per room (rate per night or season);
  - room charges;
  - each discount by name and code;
  - service charge and VAT with their rates;
  - total;
  - payments (pending ones marked "being checked");
  - refunds;
  - balance, or credit.
- **Where to open one:** staff at `/admin/bookings/[ref]/invoice`; guests at `/booking/manage/invoice`, with masked contact details.
- **Printing.** Both are print-styled; "Print or save as PDF" uses the browser.

### Refunds and reconciliation

- **Refunds** keep their four-eyes rule. The person who requests a refund can't approve it; approved refunds are then marked paid out with a reference. The booking page's **Payments** panel does all of this, plus void (`payments.void`) for desk entries made by mistake.
- **Reconciliation** is on `/admin/payments`, for a date range in Asia/Dhaka. It shows received, count, refunded, net and waiting per method, plus exceptions:
  - transfers unchecked for over 24 hours;
  - gateway amount mismatches;
  - succeeded intents without a ledger entry;
  - refused gateway notifications;
  - overpaid bookings;
  - cancelled bookings still holding money with no refund under way.

## Guest messages

### What is sent, and when

Messages are queued in the same transaction as the event, by database triggers. A message is never lost because a web request failed after the booking was saved.

| Template | Queued when | Email | WhatsApp (with consent) |
| -------- | ----------- | ----- | ----------------------- |
| `booking_confirmation` | booking created ("received" or "confirmed"), and when staff confirm it | ✓ | ✓ |
| `booking_modification` | each change to dates / rooms / party | ✓ | ✓ |
| `booking_cancellation` | booking cancelled (by guest, staff or advance expiry) | ✓ | ✓ |
| `pre_arrival` | daily at 10:00 Dhaka, for confirmed guests arriving tomorrow | ✓ | ✓ |
| `payment_confirmation` | any payment becomes confirmed (desk, verified transfer, gateway) | ✓ | ✓ |
| `payment_failure` | a reported transfer is marked not received; a gateway intent fails | ✓ | — |
| `inquiry_acknowledgment` | a website enquiry with an email address | ✓ | — |

- **No duplicates.** Each event has a `dedupe_key`, so a trigger can't queue it twice.
- **No address.** Without an email address (or WhatsApp number), the message is recorded as **No address** (`skipped`), so staff can see it and resend once they add one.
- **Templates** are in `src/lib/messaging/templates.ts`: plain-text and HTML versions, brand colours, and every database value escaped.

### Sending, retries and failure handling

- **Queue states:** `queued` → `sending` → `sent` → `delivered`. A message can also end `failed`, `skipped`, `unconfigured` or `cancelled`. Every step is logged in `message_events`.
- **Sending.** `claim_messages` locks due messages (`FOR UPDATE SKIP LOCKED`), so concurrent workers never send the same one twice. A claim whose worker died (lock older than 2 minutes) is picked up again.
- **Errors.** Network errors, HTTP 5xx, 408, 409 and 429 are retried after 4, 16, 64 and 256 minutes, capped at 6 hours, up to 5 attempts; then the message is `failed`. Other 4xx responses (for example, invalid address) fail at once with the provider's reason.
- **No provider yet.** The message becomes `unconfigured`. This doesn't use up an attempt.
- **No duplicate emails.** Email sends carry `Idempotency-Key: bsq-<outbox id>`, so a retried send can't produce a second email.
- **Delivery tracking:**
  - Resend webhooks (Svix-signed, ±5-minute timestamp window) and WhatsApp status webhooks (`X-Hub-Signature-256`) update the status to delivered, failed or bounced, and log opens and reads.
  - Each provider event id is applied once (`webhook_receipts`).
- **When messages go out:**
  - Within seconds: every booking, payment, staff action and enquiry calls `kickOutbox()` (Next `after()`).
  - The sweep `/api/jobs/messages` (Bearer `CRON_SECRET`) also expires stale payment intents.
  - Staff can also press **Send queued now**.

### Resend

`admin_resend_message` needs `bookings.write`, or `inquiries.manage` for enquiry messages.

- **Which messages qualify:** only failed, not set up, no address or cancelled ones. Sent and delivered messages can't be resent.
- **New copy:** it creates a new message to the **current** address on the booking, so corrections take effect. WhatsApp resends need the guest's consent to still be on.
- **Limits:** one resend per message (`ALREADY_RESENT`), and at most three resends of the same message in 24 hours (`RESEND_LIMIT`).
- **Logged** in the message events (with who did it) and in the booking history.

### WhatsApp

- **Click-to-chat** (`https://wa.me/<number>`) is on the website, the booking page and every email footer. No account is needed.
- **Official notifications** use the WhatsApp Business Platform Cloud API and approved templates only.
- **Consent:** guests opt in on their booking page ("Booking updates on WhatsApp"). Consent is stored per booking (`messaging_consents`, audited) and can be withdrawn at any time. Without consent, no WhatsApp message is queued. Payment problems and enquiry replies go by email only.
- **Numbers:** Bangladeshi mobile numbers are normalised to `8801XXXXXXXXX`. Guests with a non-mobile number can't opt in.

Submit these templates in WhatsApp Manager (category **Utility**, language English), then set each approved name in the matching environment variable:

| Env var | Suggested body (parameters in this order) |
| ------- | ------------------------------------------ |
| `WHATSAPP_TEMPLATE_BOOKING_CONFIRMATION` | Hello {{1}}, your booking {{2}} at Blossom Square for {{3}} to {{4}} has been {{5}}. Reply here or call us if anything changes. |
| `WHATSAPP_TEMPLATE_BOOKING_MODIFICATION` | Hello {{1}}, your booking {{2}} has been updated: {{3}} to {{4}}, total {{5}}. |
| `WHATSAPP_TEMPLATE_BOOKING_CANCELLATION` | Hello {{1}}, your booking {{2}} for {{3}} has been cancelled. Contact us if this wasn't expected. |
| `WHATSAPP_TEMPLATE_PRE_ARRIVAL` | Hello {{1}}, we look forward to welcoming you on {{2}} (booking {{3}}). Balance to pay at the hotel: {{4}}. |
| `WHATSAPP_TEMPLATE_PAYMENT_CONFIRMATION` | Hello {{1}}, we've received {{2}} for booking {{3}}. Remaining balance: {{4}}. Thank you! |

Messages outside the 24-hour customer-service window must use these templates. Staff keep replying to guests from the WhatsApp Business app as today.

## Secrets

- **Where they live:** server environment variables only, added in Vercel as **Sensitive**.
- **What `tests/security-boundaries.test.ts` enforces:**
  - none uses a `NEXT_PUBLIC_` prefix;
  - only `server-only` modules and API route handlers read them;
  - no client component imports the gateway, provider, worker or payments-data modules.
- **Never stored or logged:** credentials are not written to the database or logs. Errors returned from providers are trimmed and never include keys.
- **Admin visibility:** the admin shows only whether each variable is set (`src/lib/integrations.ts`), never its value.

| Variable | Used by |
| -------- | ------- |
| `RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_REPLY_TO`, `RESEND_WEBHOOK_SECRET` | email |
| `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_TEMPLATE_*`, `WHATSAPP_TEMPLATE_LANG`, `WHATSAPP_GRAPH_VERSION` | WhatsApp |
| `SSLCOMMERZ_STORE_ID`, `SSLCOMMERZ_STORE_PASSWORD`, `SSLCOMMERZ_SANDBOX` | card gateway |
| `BKASH_BASE_URL`, `BKASH_APP_KEY`, `BKASH_APP_SECRET`, `BKASH_USERNAME`, `BKASH_PASSWORD` | bKash gateway |
| `NAGAD_*` | reserved for the Nagad adapter |
| `CRON_SECRET` | the scheduled sweep |
